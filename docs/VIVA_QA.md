# FraudNet-Synth: Viva Q&A sheet

Generated by `python -m demo.viva_sheet`: 20 cross-cutting questions, then 90 step-by-step questions extracted from the 18 step documents. Every number here comes from a saved run (see `docs/RESULTS_ANNEXURE.md`).

## Part 1. The questions examiners are most likely to ask

1. **In one sentence, what is FraudNet-Synth?** Four simulated banks train one shared fraud detector with federated learning (Flower, FedAvg) without sharing any transactions; each bank can add synthetic fraud rows, made by CTGAN if it has enough fraud data or by an LLM if it has very little, and every synthetic row must pass the same validation gate.
2. **Why not just report accuracy?** Only 492 of 284,807 transactions (0.17%) are fraud, so a model that always answers "genuine" scores 99.83% accuracy while catching nothing. Our headline metrics are fraud-class precision, recall, F1 and PR-AUC; every arm's accuracy is about 99.9%, which tells us nothing.
3. **What exactly leaves a bank?** During training, only the model's 4,161 weights (17,478 bytes per round), its row count and scalar metrics. For the threshold, 241 pairs of integer counts. Never a transaction row or a per-transaction score. `tests/test_privacy_invariant.py` checks this on the real client code.
4. **What is your main result?** Over 5 seeds on the global test set (95 frauds), federated learning (Arm 3) reached F1 0.796 and PR-AUC 0.716, statistically the same F1 as pooling all data centrally (0.775) and only 0.011 lower PR-AUC (95% CI −0.021 to −0.001), without any bank sharing data.
5. **Who benefits most from federation?** The data-poor banks. Bank D alone (18 training frauds) reached F1 0.456; with federation the shared model reached 0.796 (+0.34 in all 5 seeds). On Bank D's own test customers it went from catching 0 of 4 frauds to 3 of 4, every seed.
6. **Did synthetic data help?** No reliable effect. 33 of 36 augmentation comparisons showed no clear difference, and the other three point in opposite directions, about what chance alone produces across 56 comparisons. We report this plainly; recent literature also reports augmentation not helping or hurting fraud models (to be verified at source).
7. **Why might augmentation not have helped?** Real fraud is already given equal total weight by our balanced loss; synthetic rows learnt from only 18–105 real frauds add little new information; the LLM never saw real rows or correlations (correlation error 0.493 vs 0.148 for CTGAN); and the validation gate removed the most extreme CTGAN rows.
8. **Why two generation modes?** A GAN needs enough examples to learn from, so data-rich Banks A and B (105 and 82 training frauds) use CTGAN. Banks C and D (28 and 18) are too small for that, so an LLM generates rows from summary statistics. This client-adaptive choice is the project's research gap.
9. **Doesn't sending prompts to Groq leak data?** We chose option (b): prompts contain only the schema and per-column mean, standard deviation and 10th/50th/90th percentiles of the bank's fraud rows, with no rows and no min/max (with 18 rows, a min or max is a single real value). The exact statistics sent are saved for audit.
10. **What does the validation gate check, and how much passed?** Schema and ranges (Pandera), edge-clamped CTGAN rows, distance to the closest real row (privacy), near-duplicates (diversity) and SDMetrics fidelity. Pass rates: A 86.8%, B 81.4%, C 78.0%, D 88.0%. No row was a near-copy of a real transaction.
11. **Why keep sentence-transformers if it doesn't work for numbers?** The design specified it, and we measured it: it rates almost every pair of rows 0.96–0.995 similar, so it can't spot copies. We kept it as a diagnostic and added a numeric distance-to-closest-record check that makes the actual decisions (D-021).
12. **What is non-IID, and how did you create it?** Banks differ in how much data and how much fraud they hold. We dealt fraud rows out by fixed quotas (A 45%, B 35%, C 12%, D 8%) and genuine rows by other quotas, giving 149 / 116 / 40 / 26 fraud rows.
13. **How does FedAvg work in one round?** The server sends the global weights; each bank trains one epoch on its own data and sends back only its weights and row count; the server averages the weights, weighted by row count; repeat for 30 rounds.
14. **How is the decision threshold chosen without sharing scores?** 241 cut-offs are fixed in advance; each bank counts its validation frauds and genuine rows above each cut-off and sends only the counts; the server adds them up and picks the best F1. A test proves this equals tuning on all banks' validation data pooled.
15. **How do you know the results aren't luck?** Every arm was run with 5 seeds, and arms were compared seed by seed with a 95% confidence interval; a difference counts only if the interval excludes zero. We also say openly that about 3 of 56 comparisons could look "clear" by chance.
16. **How do you avoid data leakage?** The test set was set aside before anything else; duplicates were removed first; synthetic rows only ever enter training data; thresholds are tuned on validation data; generators and statistics use only each bank's training rows.
17. **How do you compare with published work?** Literature reference points are about 91% federated vs 95% centralized accuracy, and FedFraud's F1 0.90 / AUC 0.96 under non-IID data (all must be verified at the source). Our accuracy (99.9%) isn't comparable because of the class imbalance; our federated ROC-AUC (0.963) is similar, and our F1 (0.80) is lower, with different data splits and models.
18. **Is the system really one system, or just scripts?** A full run started from the React dashboard went through the Node gateway (login, roles, MongoDB) and FastAPI to the four banks, streamed 300 rounds live, and gave results identical to the command-line run in all 180 metric rows.
19. **Can the model move between real computers?** Yes, for the demo: with Flower's deployment mode, each laptop ran one bank and only weights travelled over a phone hotspot. The two-laptop test passed; reported results still come from the single-machine runs for reproducibility.
20. **What are the main limitations and future work?** Small fraud counts make per-bank results noisy (Bank D's local test has 4 frauds); results come from one public dataset and one data split; weight updates themselves can leak some information. Differential privacy, secure aggregation, more clients and other datasets are future scope.

## Part 2. Step by step

### Step 0: Environment Setup and Project Orientation
*From [`STEP_00_environment_setup.md`](steps/STEP_00_environment_setup.md)*

1. **Why a virtual environment?** It isolates the project's libraries and versions from other Python projects, so the setup is reproducible.
2. **Why pin exact versions?** Flower and SDV changed their APIs across versions. Pinning makes sure the code runs the same for anyone, now and later.
3. **Why Python 3.12 and not 3.11?** 3.11 wasn't installed, 3.12 was, and every required library installed and imported on it. This is recorded as decision D-000.
4. **Why CPU-only PyTorch?** It is a project constraint (laptop, zero cost). Our models and dataset are small enough for a CPU.
5. **How does the folder structure support privacy?** Each bank has its own `data/clients/bank_x/` folder, and each federated client will load only its own path. A privacy test in Step 8 will check what clients send.

### Step 1: Data Ingestion and Exploratory Data Analysis (Phase 1)
*From [`STEP_01_data_eda.md`](steps/STEP_01_data_eda.md)*

1. **Why not use accuracy?** Fraud is 0.17% of the data. Predicting "genuine" always gives 99.83% accuracy with zero frauds caught. Precision, recall, F1 and PR-AUC focus on the fraud class.
2. **What are V1–V28?** PCA components: anonymized linear combinations of the original confidential features. They protect privacy but have no human-interpretable meaning.
3. **Difference between precision and recall?** Precision: of the alarms raised, how many were real fraud. Recall: of all real frauds, how many we caught. The bank trades them off via the decision threshold.
4. **Why PR-AUC rather than ROC-AUC as headline?** With very rare positives, ROC-AUC can look high even for weak models, because the huge number of true negatives keeps the false-positive rate tiny. PR-AUC focuses on the fraud class, and its random-guess baseline equals the fraud rate.
5. **Did EDA on the full dataset leak test information?** No modelling choice was fitted here. EDA is descriptive only. Scalers, generators and thresholds will be fitted only on training or validation data after the Step 2 split.

### Step 2: Global Split and Non-IID Partitioning into Banks A–D (Phase 1)
*From [`STEP_02_split_partition.md`](steps/STEP_02_split_partition.md)*

1. **Why split off the test set before partitioning?** So no bank, generator or scaler ever sees test data, and all six arms are scored on the identical held-out set. This prevents leakage and keeps the comparison fair.
2. **What makes your data non-IID?** Label skew (fraud rate 0.214% at A vs 0.087% at D) and quantity skew (69,546 vs 29,767 rows). Fraud *count* differs most: 149 vs 26.
3. **Why explicit quotas instead of a Dirichlet split?** Our design requires A/B to be fraud-rich and C/D fraud-poor. Quotas guarantee that, are fully reproducible and are easy to justify. A Dirichlet draw is random and might not produce that pattern.
4. **Why drop duplicates?** Identical rows split across train and test let a model score well by memorisation, which inflates results.
5. **Why does each bank also have a local test set?** To measure how well a model serves *that* bank's own customers, not just the global population. This matters for per-bank fairness, though C and D's local tests are small.

### Step 3: Shared Classifier and Sanity Baseline (Phase 1 → prepares Phase 4)
*From [`STEP_03_classifier_baseline.md`](steps/STEP_03_classifier_baseline.md)*

1. **Why an MLP and not logistic regression?** It can learn non-linear patterns, it is still tiny (4,161 weights), its weights average naturally under FedAvg, and Flower's standard examples use PyTorch.
2. **How do you handle class imbalance?** A weighted loss with fraud weight = #genuine / #fraud of the model's own training data (599 here), plus threshold tuning on validation data.
3. **Why tune the threshold on validation and not test?** Tuning on test would fit the exam itself and give an over-optimistic score. Test data is used once, only for final measurement.
4. **Why did accuracy drop when the model got better at catching fraud?** At threshold 0.5 it raised 752 false alarms out of 56,746 rows, which lowered accuracy below the useless "always genuine" model while catching 83 frauds. Accuracy hides fraud performance.
5. **Why are ROC-AUC and PR-AUC so different?** ROC-AUC counts false positives relative to 56,651 genuine rows, so 752 false alarms look tiny. PR-AUC counts them relative to the fraud alarms raised, so they matter a lot.

### Step 4: Augment Mode with CTGAN for Banks A and B (Phase 2)
*From [`STEP_04_ctgan_augment_mode.md`](steps/STEP_04_ctgan_augment_mode.md)*

1. **Why does each bank train its own CTGAN?** Training it centrally would need the banks' fraud rows in one place, which breaks the privacy invariant. Each bank's generator learns only from its own data and never leaves its folder.
2. **Why only Banks A and B?** GANs need a reasonable amount of data. With 28 and 18 training fraud rows, Banks C and D are too small, so they use Schema Mode (LLM) in Step 5.
3. **Why so many epochs?** With about 100 rows and batch size 500, ctgan performs one training step per epoch, so 2,000 epochs means only 2,000 updates, and it is cheap on CPU (~1.5–2 minutes).
4. **Do decreasing losses mean good data?** No. Generator and discriminator are opponents, so their losses don't steadily fall. Quality is judged by comparing distributions (KS here, SDMetrics in Step 6).
5. **Is "0 exact copies" enough to prove privacy?** No. A row can be a *near*-copy of a real one. Step 6 adds a distance-to-closest-record and embedding similarity check for that.

### Step 5: Schema Mode with an LLM for Banks C and D (Phase 2)
*From [`STEP_05_llm_schema_mode.md`](steps/STEP_05_llm_schema_mode.md)*

1. **How does Schema Mode protect privacy if it uses an external API?** Only aggregate statistics and the public schema are sent. No row, and not even min/max (which would be single real values). The code enforces this: the prompt builder never receives the data, the stats function refuses non-approved statistics, and tests check the prompt for real values.
2. **Why use an LLM instead of CTGAN for Banks C and D?** With 18–28 fraud rows a GAN can't learn a distribution. An LLM can produce rows from a description alone. Comparing the two modes is part of our research gap.
3. **Why did the first attempts fail?** The LLM couldn't keep count of 30 unlabelled numbers per row, and it returned wrong row counts. Strict JSON with named fields and a flexible row count fixed it.
4. **What does the 0.49 correlation difference mean?** Real fraud columns move together in certain ways. The LLM only received per-column statistics, so it generated each column almost independently and lost those relationships. CTGAN, which learns from the rows directly, kept them much better (0.15).
5. **How do you make sure the demo works without internet?** Every API reply is cached in the bank's folder. Rerunning rebuilds the candidates from the cache with zero API calls, as the final run shows.

### Step 6: Shared Validation Layer (Phase 3)
*From [`STEP_06_validation_gate.md`](steps/STEP_06_validation_gate.md)*

1. **Why one shared gate for both modes?** So the comparison between Augment and Schema mode is fair: the same rules decide what counts as acceptable synthetic data.
2. **How do you detect privacy leakage without labelled "leaks"?** With distance to closest record. The threshold is the 5th percentile of real-to-real nearest distances within the same bank, so "too close" is defined relative to how real frauds naturally cluster.
3. **Why not rely on sentence-transformers as specified?** We measured it. Text versions of numeric rows score 0.96–0.995 similarity for every kind of pair, so it can't separate copies from normal rows. We kept it as a diagnostic and added a numeric check, and we document this choice.
4. **What does "PII check" mean on an anonymised dataset?** There is no personal information in ULB, so it reduces to schema and range validation: correct columns, types, no missing values, Class = 1, plausible ranges.
5. **Why can SDMetrics only accept or refuse a whole batch?** It measures distributions of a *set* of rows, not individual rows. So it's applied to the admitted set as a whole, with a minimum score of 0.70.

### Step 7: Isolated and Centralized Arms (Phase 4)
*From [`STEP_07_isolated_centralized_arms.md`](steps/STEP_07_isolated_centralized_arms.md)*

1. **Why is centralized called an upper bound, and why is it illegal?** It sees everyone's data, the most information possible. In practice, data-protection law, competition and security risk stop banks from pooling customer transactions, so it is a reference point, not a deployable system.
2. **Why did the centralized model score a lower F1 than Bank A alone?** In this single-seed run, its threshold (tuned on 49 pooled val frauds) traded recall for precision (0.69 recall vs 0.79). Its PR-AUC, which doesn't depend on the threshold, is the highest (0.723), but only by about 0.01. Step 9's multi-seed runs will show whether the gap is real or noise.
3. **Did synthetic data help?** Not consistently. F1 changes ranged from −0.06 to +0.09, and PR-AUC changes were within ±0.015. One seed can't separate a small effect from noise, so we report it as inconclusive for now.
4. **Why tune thresholds on each owner's own validation data?** That's realistic: an isolated bank only has its own data. It also shows an honest cost of isolation: Bank D tuned on just 4 frauds and set its threshold too strictly.
5. **Why train the pooled model on local train sets, not the global train file?** The global train file also contains the banks' local validation and test rows. Training on it would leak those into training and inflate the local-test scores.

### Step 8B: Multi-Device Federated Demo (live demo only)
*From [`STEP_08B_multi_device_demo.md`](steps/STEP_08B_multi_device_demo.md)*

1. **What travels over the network?** Each round: the global model (17,478 bytes) from server to bank, and the updated weights (17,478 bytes) plus 5 scalar metrics from bank to server. After training: 241 TP and 241 FP integer counts per bank, and scalar local-test metrics. Also the code bundle once (154 KB, code and configs only).
2. **How do you know a teammate's laptop doesn't hold other banks' data?** `check_my_data` verifies the manifest's bank name and SHA-256 checksums, and that other bank folders, the raw file and the global split are absent. The client refuses to start otherwise, and 9 tests check that each unsafe set-up is refused.
3. **Doesn't handing out data files break privacy?** The handover is simulation set-up: in real life each bank already owns its data. Each teammate receives only their own bank's slice, and the privacy claim is about training, during which no row leaves any laptop.
4. **Why does each round take ~25 s on the network but ~1.3 s in simulation?** Flower deployment starts a fresh Python process (importing PyTorch) for every message on every bank. The simulation keeps workers alive. The maths is the same: results match to 2.2 × 10⁻¹⁶.
5. **Is the traffic encrypted?** No. The demo uses Flower's insecure mode on a private hotspot. The content is only weights and counts, but a real deployment would enable TLS certificates. We state this as a limitation.

### Step 8: Federated Arms with Flower (Phase 4)
*From [`STEP_08_federated_arms.md`](steps/STEP_08_federated_arms.md)*

1. **What exactly leaves a bank in FedAvg?** The 4,161 model weights (17,478 bytes per round), the number of training rows, and scalar metrics. After training, also integer TP/FP counts at fixed cut-offs and scalar local-test metrics. Never data rows or per-transaction scores. `test_privacy_invariant.py` checks this on the real client code.
2. **How is the federated threshold chosen without sharing scores?** The server fixes 241 cut-offs in advance. Each bank counts its validation frauds and genuine rows above each cut-off and sends only the counts. The server sums them and picks the best F1. Summing counts is mathematically identical to pooling the validation data.
3. **Why weight the average by row count?** A bank that trained on more examples gives a more reliable update. That's what FedAvg defines, and it makes the result close to training on the union of the data.
4. **Why 30 rounds and 1 local epoch?** One epoch limits client drift across our very unequal banks. Thirty rounds gives FedAvg time to converge, and the curve shows it plateaued by around rounds 13–15. These were decisions D-029/D-030; 30 rounds is twice the training effort of the non-federated arms, which we state openly.
5. **Why did two identical runs first give different results, and how was that fixed?** Banks train in parallel, so their replies arrive in varying order. Adding floating-point numbers in a different order gives tiny rounding differences, which training amplified. Sorting replies by bank before averaging made runs bit-identical without changing the FedAvg maths (D-032).

### Step 9: Six-Arm Experiment Runner and Results (Phase 4 → Phase 7 prep)
*From [`STEP_09_six_arm_results.md`](steps/STEP_09_six_arm_results.md)*

1. **Why 5 seeds, and what changes between them?** Five repeats give a mean ± std and paired confidence intervals at reasonable CPU cost (~22 min). A seed changes only training randomness (initial weights, batch order, FL client seeds, synthetic sample). The data split and generated pools are fixed, because regenerating LLM rows per seed isn't possible on the free tier.
2. **How do you decide a difference is real?** Paired differences across seeds with a t-based 95% CI. A difference counts only if the CI excludes 0. We also check how many seeds agree, and we account for chance across our 56 comparisons.
3. **Did augmentation help?** No, not reliably: 33 of 36 comparisons show no clear difference, and the remaining three conflict. That's a valid finding, and we report likely reasons.
4. **How far is federated from centralized?** F1 is statistically the same. PR-AUC is about 0.011 lower (CI −0.021 to −0.001). That's the measured cost of not pooling data.
5. **Why is your accuracy 99.9% when the literature says 91–95%?** On this dataset 99.83% of transactions are genuine, so accuracy is almost meaningless. That's why our headline metrics are fraud-class precision, recall, F1 and PR-AUC.

### Step 10: FastAPI Orchestration Service (Tier 3, Phase 5)
*From [`STEP_10_fastapi_orchestrator.md`](steps/STEP_10_fastapi_orchestrator.md)*

1. **Why run jobs in separate processes?** Training uses all CPU cores for minutes. A separate process can't freeze or crash the API, and jobs run one at a time so they don't slow each other down.
2. **How does the dashboard see live training?** The federated server writes one event per round to a file; the API pushes each new event to the dashboard over a WebSocket, an open connection, instead of the dashboard polling.
3. **Can the API overwrite the data our results came from?** No. Replay writes to a separate folder and only compares checksums; regeneration goes to a new versioned folder. The replay showed byte-identical files.
4. **How is privacy kept for "dataset export"?** Only validated synthetic rows (never real ones), only for one bank, and only when the gateway confirms the user is that bank's operator. Every attempt is audit-logged. This resolves a conflict between the requirements list and our privacy invariant, which we disclose (D-045).
5. **Which model answers /predict, and why?** The federated Arm 3 model (seed 42, 30 rounds). It's the privacy-preserving model, and Step 9 showed augmentation added no measurable benefit, so it's the best-evidenced choice.

### Step 11: Node.js + Express Gateway with MongoDB (Tier 2, Phase 5)
*From [`STEP_11_gateway_mongodb.md`](steps/STEP_11_gateway_mongodb.md)*

1. **Why a separate gateway instead of calling FastAPI from the browser?** Separation of concerns: user accounts, roles, history and auditing live in Tier 2. Tier 3 stays a private service on localhost with one internal key, so the ML engine is never exposed.
2. **How are passwords protected?** Only bcrypt hashes (cost 12) are stored. Login errors don't reveal whether a username exists, and attempts are rate-limited (20 per 15 minutes) and audited.
3. **How does a bank operator's export stay restricted to their own bank?** The bank comes from their signed token, not from anything they send. The gateway refuses other banks (403) and sets `X-Bank-Scope` itself, and FastAPI checks it again. A test proves a spoofed header is ignored.
4. **Why store rounds in a separate collection?** A full multi-seed run has hundreds of rounds. Separate small documents with a unique (job, arm, seed, round) index are easy to query, can't be duplicated on reconnect, and keep run documents small.
5. **What if nobody watches a run in the browser?** The gateway's own watcher records everything regardless, and it resumes watching unfinished runs after a restart.

### Step 12: React Dashboard (Tier 1, Phase 6)
*From [`STEP_12_react_dashboard.md`](steps/STEP_12_react_dashboard.md)*

1. **Why does the dashboard never call FastAPI directly?** The gateway is the single entry point that checks logins and roles and keeps history. FastAPI stays private on localhost with its internal key.
2. **If a viewer edits the page to show the "Start run" button, can they start a run?** No. Hiding the button is only convenience; the gateway checks the role on every request and returns 403 (tested in Step 11).
3. **How do live charts work?** The browser opens a WebSocket to the gateway. The gateway first replays the rounds already stored in MongoDB, then forwards each new round as FastAPI reports it, and React adds a point to the chart.
4. **Why is accuracy greyed out?** 99.83% of test transactions are genuine, so every model reaches about 99.9% accuracy. Fraud-class F1, precision, recall and PR-AUC are the meaningful measures.
5. **Where is the login token kept?** In memory and in the tab's sessionStorage: it survives a refresh but disappears when the tab closes, and it expires after 8 hours.

*From [`STEP_13_integration_evaluation.md`](steps/STEP_13_integration_evaluation.md)*

1. **How do you know the dashboard didn't change the results?** We compared all 180 metric rows of the dashboard run with the command-line run: the maximum difference was exactly 0.
2. **What path does a "Start run" click take?** Browser → gateway (JWT login, admin role check, stored in MongoDB, audited) → FastAPI job → Flower simulation of the four banks; live rounds come back over WebSockets.

### Step 14: Testing, documentation and demo hardening (Phase 8)
*From [`STEP_14_testing_docs_demo.md`](steps/STEP_14_testing_docs_demo.md)*

### Extension E1: q-FedAvg vs FedAvg, per-bank fairness (optional, beyond the synopsis)
*From [`STEP_E1_qfedavg.md`](steps/STEP_E1_qfedavg.md)*

1. **What is q-FedAvg?** An FL aggregation rule that gives more weight to clients where the global model's loss is higher; q controls how strongly. q = 0 gives every client an equal say.
2. **Did it improve fairness?** No. No q improved the worst bank's F1; q = 2 made it clearly worse (−0.063, 95% CI −0.108 to −0.018).
3. **Why not?** The per-bank losses of the global model were nearly equal (max/min ratio ≤ 1.17) because our balanced weighted loss equalises the classes in every bank, so q-FedAvg had no signal; Bank D even had the lowest loss by round 30.
4. **Why did you tune L, and on what data?** Flower sets L = 1 / learning rate = 1000 for our Adam clients, which froze training (PR-AUC stayed 0.005). We chose L from {1, 3, 10} by pooled validation F1, never test data.
5. **Is q = 0 the same as FedAvg?** No: q = 0 averages banks equally, while our FedAvg weights them by row count. That's why both were run.

### Extension E2: conformal risk control of the miss rate, global vs per-bank (optional, beyond the synopsis)
*From [`STEP_E2_conformal.md`](steps/STEP_E2_conformal.md)*

1. **What does conformal risk control guarantee?** That the expected miss rate on new frauds is at most α, if new frauds are exchangeable with the calibration frauds. It's an average guarantee, not a promise for every test set.
2. **Why did α = 0.05 give 5.5% misses on the test set, above 5%?** The guarantee holds on average over calibration sets; one fixed split can land above α. Our resampling check averaged 3.5% at α = 0.05.
3. **Why must Banks C and D flag everything at α = 0.10?** With n calibration frauds the smallest certifiable α is 1/(n+1): 1/7 ≈ 0.143 for C and 1/5 = 0.20 for D.
4. **How is global calibration private?** Each bank sends only counts of its validation frauds below fixed cut-offs; the server sums them, as for the federated threshold.
5. **What's the cost of a strict guarantee?** Many false alarms: at α = 0.10, 18.6% of transactions are flagged and precision drops to about 0.01, versus 0.15% flagged and precision 0.84 with the F1-tuned threshold.
