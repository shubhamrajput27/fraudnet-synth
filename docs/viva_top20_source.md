1. **In one sentence, what is FraudNet-Synth?** Four simulated banks train one shared fraud detector with federated learning (Flower, FedAvg) without sharing any transactions; each bank can add synthetic fraud rows, made by CTGAN if it has enough fraud data or by an LLM if it has very little, and every synthetic row must pass the same validation gate.
2. **Why not just report accuracy?** Only 492 of 284,807 transactions (0.17%) are fraud, so a model that always answers "genuine" scores 99.83% accuracy while catching nothing. Our headline metrics are fraud-class precision, recall, F1 and PR-AUC; every arm's accuracy is about 99.9%, which tells us nothing.
3. **What exactly leaves a bank?** During training, only the model's 4,161 weights (17,478 bytes per round), its row count and scalar metrics. For the threshold, 241 pairs of integer counts. Never a transaction row or a per-transaction score. `tests/test_privacy_invariant.py` checks this on the real client code.
4. **What is your main result?** Over 5 seeds on the global test set (95 frauds), federated learning (Arm 3) reached F1 0.796 and PR-AUC 0.716, statistically the same F1 as pooling all data centrally (0.775) and only 0.011 lower PR-AUC (95% CI −0.021 to −0.001), without any bank sharing data.
5. **Who benefits most from federation?** The data-poor banks. Bank D alone (18 training frauds) reached F1 0.456; with federation the shared model reached 0.796 (+0.34 in all 5 seeds). On Bank D's own test customers it went from catching 0 of 4 frauds to 3 of 4, every seed.
6. **Did synthetic data help?** No reliable effect. 33 of 36 augmentation comparisons showed no clear difference, and the other three point in opposite directions, about what chance alone produces across 56 comparisons. We report this plainly; recent literature also reports augmentation not helping or hurting fraud models (to be verified at source).
7. **Why might augmentation not have helped?** Real fraud is already given equal total weight by our balanced loss; synthetic rows learnt from only 18–105 real frauds add little new information; the LLM never saw real rows or correlations (correlation error 0.493 vs 0.148 for CTGAN); and the validation gate removed the most extreme CTGAN rows.
8. **Why two generation modes?** A GAN needs enough examples to learn from, so data-rich Banks A and B (105 and 82 training frauds) use CTGAN. Banks C and D (28 and 18) are too small for that, so an LLM generates rows from summary statistics. This client-adaptive choice is the project's research gap.
9. **Doesn't sending prompts to Groq leak data?** We chose option (b): prompts contain only the schema and per-column mean, standard deviation and 10th/50th/90th percentiles of the bank's fraud rows, with no rows and no min/max (with 18 rows, a min or max is a single real value). The exact statistics sent are saved for audit.
10. **What does the validation gate check, and how much passed?** Schema and ranges (Pandera), edge-clamped CTGAN rows, distance to the closest real row (privacy), near-duplicates (diversity) and SDMetrics fidelity. Pass rates: A 86.8%, B 81.4%, C 78.0%, D 88.0%. No row was a near-copy of a real transaction.
11. **Why keep sentence-transformers if it doesn't work for numbers?** The design specified it, and we measured it: it rates almost every pair of rows 0.96–0.995 similar, so it can't spot copies. We kept it as a diagnostic and added a numeric distance-to-closest-record check that makes the actual decisions (D-021).
12. **What is non-IID, and how did you create it?** Banks differ in how much data and how much fraud they hold. We dealt fraud rows out by fixed quotas (A 45%, B 35%, C 12%, D 8%) and genuine rows by other quotas, giving 149 / 116 / 40 / 26 fraud rows.
13. **How does FedAvg work in one round?** The server sends the global weights; each bank trains one epoch on its own data and sends back only its weights and row count; the server averages the weights, weighted by row count; repeat for 30 rounds.
14. **How is the decision threshold chosen without sharing scores?** 241 cut-offs are fixed in advance; each bank counts its validation frauds and genuine rows above each cut-off and sends only the counts; the server adds them up and picks the best F1. A test proves this equals tuning on all banks' validation data pooled.
15. **How do you know the results aren't luck?** Every arm was run with 5 seeds, and arms were compared seed by seed with a 95% confidence interval; a difference counts only if the interval excludes zero. We also say openly that about 3 of 56 comparisons could look "clear" by chance.
16. **How do you avoid data leakage?** The test set was set aside before anything else; duplicates were removed first; synthetic rows only ever enter training data; thresholds are tuned on validation data; generators and statistics use only each bank's training rows.
17. **How do you compare with published work?** Literature reference points are about 91% federated vs 95% centralized accuracy, and FedFraud's F1 0.90 / AUC 0.96 under non-IID data (all must be verified at the source). Our accuracy (99.9%) isn't comparable because of the class imbalance; our federated ROC-AUC (0.963) is similar, and our F1 (0.80) is lower, with different data splits and models.
18. **Is the system really one system, or just scripts?** A full run started from the React dashboard went through the Node gateway (login, roles, MongoDB) and FastAPI to the four banks, streamed 300 rounds live, and gave results identical to the command-line run in all 180 metric rows.
19. **Can the model move between real computers?** Yes, for the demo: with Flower's deployment mode, each laptop ran one bank and only weights travelled over a phone hotspot. The two-laptop test passed; reported results still come from the single-machine runs for reproducibility.
20. **What are the main limitations and future work?** Small fraud counts make per-bank results noisy (Bank D's local test has 4 frauds); results come from one public dataset and one data split; weight updates themselves can leak some information. Differential privacy, secure aggregation, more clients and other datasets are future scope.
